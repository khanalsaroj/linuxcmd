A compatibility layer, not a Linux environment.

Command behavior is implemented natively in Go on top of the Windows filesystem and Win32 APIs, rather than emulating or virtualizing Linux underneath it.

What runs

  • +Real Windows executables backed by the Go standard library and Windows syscalls
  • +The cmd.exe window you already have open, with its own pipes and redirection
  • +Linux-style flags, exit codes, and error text such as No such file or directory
  • +Paths written the Linux way, resolved to real Windows paths

What does not

  • −No WSL, and nothing to enable at the OS level
  • −No Cygwin, MSYS2, or Git Bash runtime
  • −No virtual machine and no second filesystem to keep in sync
  • −No shelling out to cmd.exe /c behind your back

One binary, 193 hardlinks.

Exactly one Go program is compiled. Every command on your PATH is a hardlink to that same file, which reads its own invoked filename to decide what to run. BusyBox uses the same technique on Linux.

ls -la /tmp
↓ argv[0] = "ls.exe" → command name "ls"
↓ internal/parser → {l:true, a:true}, args ["/tmp"]
↓ internal/paths → "/tmp" becomes a real Windows path
↓ os.ReadDir/os.Stat → the NTFS filesystem, directly
↓ internal/output → drwxr-xr-x ... Aug 17 12:30 name

  • Small on disk

    Hardlinks share the same on-disk data, so 193 separate executables cost the space of one, not 193 copies.

  • Fast to start

    Every command is a native Windows process launch. No interpreter, and no shim spawning a second process.

  • Cheap to extend

    A new command is one file in commands/ that calls command.Register in an init() function. The build script and installer find it through linuxcmd --list-commands.

Linux path syntax, resolved to real Windows paths.

Windows has no single filesystem root shared across drives, so Linux path syntax is translated rather than faked. Output always shows the real Windows path.

  • ~/Documents→%USERPROFILE%\Documents
  • /tmp/foo→%TEMP%\foo
  • /dev/null→NUL
  • /c/Users/x→C:\Users\x
  • C:/x→C:\x
  • /etc→<current drive>:\etc

cmd.exe never expands * or ? before running a program, so each command expands its own wildcards. rm *.txt behaves the way you expect, and an argument that matches nothing is passed through untouched so real typos still produce a real error.

Install in one line. No admin rights.

The installer verifies the release checksum, drops the binaries in %LOCALAPPDATA%, and adds that directory to your user PATH. Nothing outside your own registry hive is touched.

The parts that are honest approximations.

Windows genuinely does not have some of the concepts these commands are built on. Where that happens, the gap is documented rather than hidden.

cd, mkdir, rmdir and echo are shadowed by cmd.exe builtins

cmd.exe resolves its own builtins before it ever looks at PATH, and that order is hard-wired into its parser. So cd.exe, mkdir.exe, rmdir.exe and echo.exe are complete working programs, usable through linuxcmd cd ..., from scripts, or by typing the extension, but typing cd bare still runs the builtin unless you opt in to the DOSKEY layer with -EnableDoskeyOverrides.

It stays opt-in because it is a small persistent change applied to every new interactive CMD session, registered through the documented HKCU AutoRun extension point. The installer appends its hook to any existing AutoRun value instead of replacing it, and removes only its own segment on uninstall.

cd is special even then. No child process can change its parent shell's working directory on any operating system, which is exactly why every Unix shell implements cd as a builtin too. Here cd.exe resolves the Linux-style path and prints it, and the macro feeds that back into the builtin inside the same process: 

cd=for /f "usebackq delims=" %i in (`"%LINUXCMD_HOME%\cd.exe" $*`) do @cd /d "%i"

DOSKEY macros only expand for lines typed at an interactive prompt, so this layer cannot change the behavior of any existing .bat or .cmd file.

Permission bits are approximated, not faked

Windows has no POSIX rwxrwxrwx model. ls -l shows the real entry type, then derives a single rwx-style triplet from the read-only attribute and repeats it three times, because Windows draws no owner, group, and other distinction. Link counts always read 1, and owner and group both show the current Windows username.

kill has no signal semantics

Every invocation maps onto TerminateProcess. Windows draws no SIGTERM against SIGKILL distinction for arbitrary processes, so neither does this.

ping wraps the real Windows ping.exe

Raw ICMP needs elevated privileges on Windows, so ping calls the system ping.exe by explicit System32 path with separated arguments, never a shell string. Only -c is translated; other flags pass through as they are. A handful of other commands do the same for the same reason, including traceroute, netstat, systemctl and journalctl.

grep uses RE2, and ip is read-only

grep uses Go's regexp package, which is close to POSIX extended but has no backreferences and no lookaround.

ip covers ip addr and ip link over Go's net package. There is no iproute2 on Windows to wrap, and route or tunnel modification is out of scope.

Pipelines and redirection come from cmd.exe, not from here

These are ordinary executables reading real stdin and writing real stdout, so cmd.exe's own |, > and >> already work with all of them today. There is no built-in pipeline parser yet. The Context{Stdin,Stdout,Stderr} design exists so one can be added later without reworking any command.

Where this sits next to WSL and Git Bash.

WSL and Git Bash solve a broader problem, and solve it well. This solves one narrow thing: familiar commands inside the terminal you already have open.

Written in Go, built to be read.

The command registry, flag parser, and path layer are all plain Go. Reading one command's source is genuinely enough to write the next one, and the build script picks it up with no other file to edit.
